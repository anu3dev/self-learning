A production GenAI solution is not just a model call. It is a pipeline of **data preparation, retrieval, prompt construction, model inference, tool execution, safety checks, evaluation, and operations**.

## The core decision map

```text
Need a managed foundation model API?
    → Amazon Bedrock

Need to host/customize a model with infrastructure and serving control?
    → Amazon SageMaker AI

Need answers grounded in enterprise documents?
    → RAG / Amazon Bedrock Knowledge Bases

Need the model to call business APIs?
    → Bedrock Agents action groups, client-side tool use, MCP, or AgentCore Gateway

Need deterministic multi-step orchestration?
    → AWS Step Functions or Amazon Bedrock Flows

Need reusable, versioned prompts?
    → Amazon Bedrock Prompt Management

Need safety policies around input/output?
    → Amazon Bedrock Guardrails + application validation

Need to prove output quality before release?
    → Bedrock evaluations + automated regression gate + human review for ambiguous cases
```

# 1. FOUNDATION MODELS: SELECT THE RIGHT MODEL AND API

## 1.1 Amazon Bedrock vs SageMaker AI

| Requirement | Better starting point | Why |
|---|---|---|
| Call supported foundation models through a managed API | Amazon Bedrock | Model access without managing model-serving infrastructure |
| Use managed model families, inference profiles, Guardrails, Knowledge Bases, Prompt Management, Flows, or Agents | Amazon Bedrock | Integrated GenAI application services |
| Host an open-weight model, control serving container, GPU configuration, batching, tensor parallelism, or endpoint scaling | SageMaker AI | More control over model deployment and serving |
| Serve a very large model whose artifacts are tens or hundreds of GB | SageMaker real-time endpoint with an LMI container may fit | Model-serving optimizations and GPU infrastructure can be configured |
| Need a custom model endpoint and model package approval workflow | SageMaker AI Model Registry / model package group | Release governance and explicit approval status |

**Exam clue:** “We need to control the container, GPU topology, tensor parallelism, continuous batching, or endpoint scaling” points toward SageMaker AI. “We want a managed FM API and Bedrock-native RAG/Guardrails/Prompt Management” points toward Bedrock.

## 1.2 Model selection checklist

Before selecting a model, verify:

- **Region availability:** Is the model or inference profile available in the target Region?
- **Modality:** Text, image, audio, video, or multimodal input/output?
- **Context window:** Can it accept the system prompt, conversation history, retrieved chunks, and tool descriptions?
- **API compatibility:** Does the model support the intended operation, such as `Converse`, `ConverseStream`, or `InvokeModel`?
- **Streaming support:** Is streaming required by the user experience?
- **Latency and throughput:** Does it meet p95 latency and peak concurrency needs?
- **Quality:** Does it pass a representative task-specific evaluation set?
- **Cost:** What are input/output token costs, cache benefits, and expected request volume?
- **Safety and policy:** Does it support the needed guardrail and operational pattern?
- **Output structure:** Can it reliably produce the required JSON/schema or does the application need validation and repair?

Use model cards and the Bedrock model catalog as a shortlist—not as a substitute for benchmarking your own task.

## 1.3 `Converse` vs `ConverseStream` vs `InvokeModel`

| API | Mental model | Choose when |
|---|---|---|
| `Converse` | Common conversation interface | Multi-turn chat, messages, system prompt, tool use, and consistent request structure across supported models |
| `ConverseStream` | Streaming version of the conversation interface | Show generated text as it arrives; measure time to first token |
| `InvokeModel` | Model-specific request/response body | A model requires a model-specific payload or exposes a capability/configuration through its native schema |
| `InvokeModelWithResponseStream` | Streaming model-specific invocation | Model-specific request body plus streaming response is required |
| `StartAsyncInvoke` | Submit work for asynchronous processing | Long-running or asynchronous supported inference workflows where the result is retrieved later |

### Common traps

- Do not assume every model supports every operation. Verify the model's supported API.
- `Converse` reduces model-specific branching, but model-specific fields may still be passed through supported additional request fields.
- Use `ConverseStream` when the UX requires incremental tokens. Do not measure a non-streaming response with a streaming-only metric.
- Use `InvokeModel` for image-generation models when the required request is a model-specific JSON body such as `imageGenerationConfig`.
- For long-running report generation, asynchronous invocation may be a better API pattern than holding an ordinary synchronous request open.

## 1.4 Model parameters and generation behavior

| Parameter | Effect | Typical adjustment |
|---|---|---|
| Temperature | Controls randomness in token selection | Lower for stable, constrained answers; raise gradually for creative variation |
| `top_p` | Nucleus sampling; restricts candidates to a probability mass | Tune alongside temperature, not blindly |
| `top_k` | Restricts sampling to the top K candidate tokens for models that support it | Broader candidate set can increase variation |
| Maximum output tokens | Caps response length | Set enough for the task; too low truncates answers and too high can waste cost |
| Seed, where supported | Helps reproduce a generation configuration | Useful for controlled experiments; does not guarantee identical behavior in every setup |

**Do not use “raise temperature” as a generic fix.** First determine whether the problem is insufficient diversity, poor grounding, retrieval failure, prompt ambiguity, or model capability.

## 1.5 Embedding models

An embedding model maps text to a numeric vector so semantically related content can be compared.

```text
Document section
    |
    v
Embedding model
    |
    v
Vector [d1, d2, d3, ...]
    |
    v
Vector index
```

- Choose embedding dimensions supported by the selected model.
- Store the embedding model and dimensions as part of index configuration.
- Query embeddings and indexed document embeddings must use a compatible embedding space.
- If the embedding model or preprocessing pipeline changes, plan a **consistent re-embedding and re-indexing strategy**. A partial refresh can leave old and new vectors in incompatible semantic spaces and cause retrieval drift.
- A vector index must be configured with the required vector field, dimensions, text/chunk field, and metadata field expected by the selected integration.

# 2. AMAZON BEDROCK PROMPT MANAGEMENT

## 2.1 Why use Prompt Management?

Use managed prompts when several applications need shared instructions, templates, variables, variants, and controlled releases.

```text
Prompt source / draft
        |
        v
Create reusable managed prompt
        |
        v
Variables + variants
        |
        v
Test on development dataset
        |
        v
Offline evaluation / review
        |
        v
Create approved prompt version
        |
        v
Invoke version / ARN from application
```

### Important concepts

- **Prompt template:** Reusable instruction structure.
- **Variables:** Runtime values injected into the prompt.
- **Variants:** Alternative prompt configurations to compare.
- **Version:** An immutable released version of the prompt configuration.
- **Prompt version ARN/reference:** Lets an application invoke the approved version rather than silently consuming an evolving draft.
- **S3 Versioning:** Useful for retaining prompt-source history when files in S3 are the source of truth.
- **CloudTrail:** Use the appropriate event selectors to audit prompt-management operations when required by the scenario.

## 2.2 Prompt engineering structure

A robust prompt typically has:

1. **Role/task:** What the model should do.
2. **Context:** Business rules, retrieved evidence, or user-provided information.
3. **Instructions:** Clear, ordered constraints.
4. **Input delimiters:** Mark untrusted user content and retrieved content clearly.
5. **Output contract:** JSON schema, fields, format, length, or required citations.
6. **Uncertainty behavior:** State when evidence is insufficient; do not invent facts.
7. **Examples:** Add only when they improve consistency.
8. **Safety boundaries:** Explicitly prohibit unsupported actions or disclosure.

Use a representative development set to compare variants, then verify the selected prompt on a **hold-out set**. Testing only on the same examples used to tune the prompt can overfit the prompt to those examples.

## 2.3 Prompt regression testing

A wording change can cause style drift, missed citations, or changed behavior even when the model is unchanged.

```text
Candidate prompt version
        |
        v
Fixed evaluation prompt set
        |
        v
Invoke candidate
        |
        v
Score output / compare references
        |
        v
Store metrics
        |
        v
Threshold check
   |            |
 PASS          FAIL
   |            |
 Promote       Stop release
```

A Step Functions workflow is useful when the release gate must orchestrate multiple steps—candidate invocation, scoring, persistence, and a pass/fail result. Bedrock evaluation jobs can provide managed evaluation, but a report that someone manually reviews is not an automated CI/CD gate by itself.

## 2.4 Prompt caching vs response/semantic caching

| Technique | What is reused? | Main use |
|---|---|---|
| Bedrock prompt caching | Eligible repeated prompt-prefix/context processing, where supported | Reduce repeated input processing and latency/cost |
| Exact response cache | A response for the exact normalized request key | Repeated identical requests |
| Semantic response cache | A previous answer for a sufficiently similar question | Paraphrased questions with the same meaning |

Prompt caching is **not** the same as caching a final answer. Semantic response caching must include metadata that defines the cache boundary.

Example cache key/filter dimensions:
- Article/document ID
- Locale/language
- Subscriber tier or authorization scope
- Content version
- Similarity threshold

If you omit the subscriber tier, you can leak an answer generated for a different entitlement. If you omit the content version, you can serve stale answers after the source changes. Use a conservative similarity threshold and test false matches.

# 3. AMAZON BEDROCK FLOWS AND ORCHESTRATION

## 3.1 Bedrock Flows

Use a Flow when the application is a visual, managed sequence of model prompts and conditional steps.

```text
Input
  |
  v
Prompt / FM node
  |
  v
Condition node
  |------------------|
  v                  v
Task A prompt      Task B prompt
  |                  |
  +--------+---------+
           v
         Output
```

A typical pattern:
- Normalize or classify a request.
- Use a **Condition** node to route by category.
- Invoke a task-specific prompt/model.
- Publish a Flow version.
- Invoke the production version or alias rather than relying on an unapproved draft.

Flows are useful for managed branching among prompt/model steps. Use Step Functions when the process needs broader AWS workflow features such as callbacks, long-running approvals, retries, parallel tasks, and service integrations.

## 3.2 Step Functions

Use Step Functions for deterministic workflow orchestration around AI tasks.

| State/pattern | Use |
|---|---|
| `Choice` | Branch based on classification, score, status, or business rule |
| `Parallel` | Run independent assessments at the same time |
| `Retry` | Retry transient failures with controlled backoff |
| `Catch` | Route errors to recovery or escalation |
| Lambda task | Run custom preprocessing, tool calls, scoring, or integration logic |
| Callback with task token | Pause until an external human/system approval completes |
| Standard workflow | Long-running, durable workflows and callback patterns |

### Human approval with callback token

```text
Step Functions task (waitForTaskToken)
        |
        v
Lambda sends approval link + task token
        |
        v
Human reviewer / approval API
        |
        v
API Gateway -> Lambda
        |
        +--> SendTaskSuccess
        |
        +--> SendTaskFailure
```

- Pass the task token to the callback system securely.
- Do not expose task tokens in public logs or allow unauthorized callers to submit them.
- Use `SendTaskSuccess` or `SendTaskFailure` after the approval decision.
- This pattern is appropriate when the workflow must wait for human review, such as regulated classification or approval before publishing.

## 3.3 EventBridge, SQS, and failure handling

- **EventBridge:** Event routing and event-driven integration. Publish domain events such as `descriptionGenerated` and route them to subscribers.
- **SQS:** Durable queue and buffering between producer and worker.
- **Dead-letter queue (DLQ):** Captures messages/events that could not be delivered or processed under the configured policy.
- **Lambda on-failure destination:** Records failed asynchronous Lambda invocation outcomes.
- **Idempotency:** Workers must safely handle retries and duplicate delivery, especially for payment, claims, settlement, and other side-effecting operations.

Use EventBridge when an event should fan out to event consumers. Use SQS when work should wait in a queue and be processed at a controlled pace. They solve related but different problems.

# 4. RAG FUNDAMENTALS

## 4.1 What is Retrieval-Augmented Generation?

RAG retrieves relevant external knowledge and places it in the model context so the model can answer using that evidence.

```text
OFFLINE / INGESTION
Documents
   |
   v
Parse / normalize
   |
   v
Chunk
   |
   v
Embedding model
   |
   v
Vector index + metadata

ONLINE / QUERY
User question
   |
   v
Query normalization / decomposition
   |
   v
Retrieve candidates
   |
   v
Filter / rerank / select context
   |
   v
Prompt + retrieved evidence
   |
   v
Foundation model
   |
   v
Answer + citations / references
```

RAG does not guarantee truth. Retrieval can miss evidence, the source can be stale, or the model can make claims unsupported by the retrieved chunks. Evaluation must measure both retrieval quality and generated-answer quality.

## 4.2 Knowledge Base: `Retrieve` vs `RetrieveAndGenerate`

| Operation | What it does | Best use |
|---|---|---|
| `Retrieve` | Returns matching source chunks and result metadata without generating a natural-language answer | Debug retrieval, inspect ranking, content, metadata, source location, and relevancy score |
| `RetrieveAndGenerate` | Retrieves context and asks a model to generate an answer, often with citations | Production RAG answer with generated text and source references |

**Exam clue:** If the team must isolate retrieval quality and avoid generation variability, use `Retrieve` first. Inspect `retrievalResults`, including content, metadata, location, and score.

Use `RetrieveAndGenerate` when the requirement is a user-facing answer grounded in retrieved evidence. Render citations using the returned references rather than inventing source links.

## 4.3 Chunking strategies

| Strategy | How it works | Good fit | Tradeoff |
|---|---|---|---|
| Fixed-size | Split text by configured size and overlap | Predictable segmentation and simple ingestion | Can split definitions, procedures, and exceptions across arbitrary boundaries |
| Hierarchical | Retrieve small child chunks while returning larger parent context | Precise question matching that still needs surrounding section context | Requires a parent/child structure and appropriate configuration |
| Semantic | Uses semantic boundaries to create meaningful chunks | Documents where fixed token windows create poor boundaries | Does not automatically solve every need for parent-level context |
| None | Avoid automatic chunking; treat input as a larger unit or provide custom processing | Custom pre-segmentation/processing or data already segmented appropriately | Large chunks reduce precise retrieval; may need custom preprocessing |

### Chunking clues

- “Find a short procedure precisely but include definitions/exceptions nearby” → consider **hierarchical chunking**.
- “Simple predictable segmentation and overlap” → fixed-size.
- “Paragraph boundaries should follow meaning” → semantic.
- “We need custom segmentation/metadata enrichment after parsing” → no managed chunking plus a supported custom transformation pipeline may be appropriate.
- Choose chunking when configuring the data source. Changing it later typically requires re-ingestion/re-indexing.

## 4.4 Metadata filtering

Metadata helps retrieval respect source boundaries, version, jurisdiction, language, document type, and access scope.

Example:

```json
{
  "jurisdiction": "US-MN",
  "documentType": "policy",
  "edition": "2026",
  "sourceId": "POL-1042",
  "documentVersion": "v7"
}
```

A metadata sidecar for an S3 document uses the source document filename plus the metadata suffix (for example, `policy.pdf.metadata.json`), with the metadata fields declared in the expected structure. Configure the metadata prefix where required by the S3 data-source setup.

- Use an `andAll`-style filter when **all** conditions must match.
- Keep metadata fields stable and meaningful.
- Include document version when stale-source answers are unacceptable.
- Do not rely on the model to enforce tenant, subscriber-tier, or authorization boundaries. Apply access filtering before using retrieved content.
- Metadata supports traceability; record source IDs and document versions with the retrieved chunks and final answer.

## 4.5 Hybrid search and reranking

- **Vector/semantic search:** Finds semantically similar content even when exact terms differ.
- **Keyword/BM25 search:** Helps match exact terms, codes, product IDs, legal phrases, or technical identifiers.
- **Hybrid search:** Combines semantic and lexical retrieval where supported.
- **Reranking:** Re-scores/reorders candidate chunks so the most relevant candidates rise to the top.

Reranking is an optimization—not the first debugging step. Establish a baseline with `Retrieve`, fixed test queries, expected passages, and result scores before adding reranking. Otherwise it is difficult to tell whether the original problem was ingestion, query formulation, metadata filtering, retrieval, or generation.

## 4.6 Query decomposition and multi-step retrieval

Some questions contain several sub-questions or require evidence from separate sections.

```text
Complex user question
        |
        v
Decompose into subqueries
   |       |       |
   v       v       v
Retrieve Retrieve Retrieve
   |       |       |
   +-------+-------+
           |
           v
Deduplicate / aggregate evidence
           |
           v
Generate one answer with source traceability
```

A Lambda plus Step Functions pipeline can decompose a question, call `Retrieve` for each subquery, and aggregate the chunks when the existing architecture needs custom control. Use the managed agentic-retrieval feature only when its documented prerequisites fit the knowledge-base type and existing architecture; do not assume it works with every custom vector-store setup.

## 4.7 Knowledge Base data sources and ingestion

Knowledge Bases can use supported data sources/connectors such as S3 and supported enterprise sources (for example, Confluence where available/configured). The application should distinguish **adding/updating source content** from **making the vector index query-ready**.

```text
Source content changed
        |
        v
StartIngestionJob
        |
        v
Poll GetIngestionJob
        |
        v
Wait for terminal success status
        |
        v
Review ingestion statistics/errors
        |
        v
Run retrieval-readiness checks
```

- Do not assume that changing an S3 object means the vector index has immediately refreshed.
- Capture job status and ingestion statistics.
- Retry query-readiness checks after ingestion completes.
- For scheduled syncs, schedule the ingestion workflow and poll until the job reaches a terminal state.
- For source formats that require OCR, transcription, or structured extraction, preprocess with the appropriate service before indexing.

## 4.8 Vector store configuration

For a customer-managed OpenSearch vector store, the index and knowledge-base configuration must agree on:
- Vector field name and vector dimensions
- Text/chunk field
- Metadata field
- Collection/endpoint and index name
- Supported engine/configuration, such as FAISS where required by the selected integration
- Access policy, IAM permissions, network access, and encryption

Do not treat the vector store as “just an index.” A mismatch between embedding dimensions and the vector field, or between the expected metadata/text fields and the actual mapping, can prevent deployment or break retrieval.

## 4.9 Custom ingestion transformations

Use a custom transformation when you must enrich metadata, apply organization-specific segmentation, or transform parsed content beyond the managed default.

The source-paper pattern uses a configuration with no managed chunking and a Lambda custom transformation at the appropriate post-chunking stage, with S3 intermediate storage where required. Follow the exact supported stage and payload contract in current documentation.

Use managed parsing/chunking when it meets the need; custom transformation adds code, retries, testing, permissions, and operational burden.

## 4.10 Citation quality and traceability

A grounded response should retain:
- Generated response text
- Retrieved reference/source locations
- Source/document ID and version
- Relevant chunk content or trace identifier
- Model/prompt version and request metadata, where appropriate

For audit-sensitive use cases, catalog approved sources in Glue Data Catalog where suitable, attach document-level source attributes during ingestion, and preserve the references returned by RAG. A citation existing is not proof that the answer is supported: compare each factual claim with the actual retrieved content.

# 5. EMBEDDINGS, VECTOR SEARCH, AND INDEX OPERATIONS

## 5.1 Embedding model and vector dimensions

The embedding model used for indexing must be compatible with the query embedding model. If you change the embedding model, dimensions, tokenization, or preprocessing pipeline, plan a complete and consistent re-embedding/re-indexing strategy unless the platform explicitly supports a safe migration path.

**Trap:** Re-embedding only newly added paragraphs can mix old and new semantic spaces. A narrow test set may look fine while queries across older documents silently degrade.

## 5.2 OpenSearch and vector index decisions

- Separate indices by domain when isolation, distinct schemas, lifecycle, or index-level scaling requires it.
- Plan primary shard counts around the data-node layout and expected corpus/query workload.
- Verify `collectionARN`, index name, vector field, text field, metadata field, engine, and dimensions during deployment.
- Add deployment gates so the app does not go live with a missing or incompatible vector index.
- Binary embeddings should be enabled only when the embedding model and target vector store support the selected binary representation. Do not assume all model/store combinations support it.

## 5.3 Managed vs custom retrieval

Choose managed Knowledge Bases when the supported data source, vector store, chunking, retrieval, and generation path meets requirements. Choose custom retrieval when you need an existing proprietary search engine, special query decomposition, custom ranking, or behavior outside the managed path.

A custom retrieval design carries responsibility for:
- Index updates
- Metadata filters and authorization
- Embedding model consistency
- Retry/error handling
- Reranking and relevance tests
- Citation/source traceability
- Evaluation datasets and metrics

# 6. AMAZON BEDROCK GUARDRAILS AND INPUT/OUTPUT SAFETY

## 6.1 Guardrails are a layer, not the entire security design

Guardrails can apply supported safety controls to model input/output. They do not replace authentication, authorization, API validation, PII handling in tools/logs, network restrictions, or application-level output validation.

```text
Request
  |
  v
API schema validation
  |
  v
Normalize / inspect input
  |
  v
Guardrail input checks
  |
  v
Model / tool execution
  |
  v
Guardrail output checks
  |
  v
Validate schema + redact if needed
  |
  v
Audit-safe logging
  |
  v
Return response
```

## 6.2 Common guardrail controls

| Requirement | Control to consider |
|---|---|
| Block unsafe categories such as violence or insults | Managed content filters; apply the output action when the unsafe text is generated |
| Restrict certain topics | Denied topics |
| Detect or mask personal information | Sensitive information/PII filters |
| Detect a known customer/loyalty identifier pattern | Regular-expression filter, where supported |
| Detect prompt injection or prompt attacks | Prompt-attack protection plus input normalization and adversarial tests |
| Reduce unsupported RAG claims | Contextual grounding/relevance checks where supported |
| Reuse centrally managed controls across accounts | Guardrail resource policy and caller IAM permission, with the appropriate cross-account setup |

**Block vs Mask/Anonymize**
- **Block:** Stop the unsafe input/output from proceeding or being returned.
- **Mask/Anonymize:** Replace sensitive values according to the configured behavior so processing can continue with reduced exposure.
- The action should match the policy: blocking violent generated code comments is an output control; PII handling may require both input and output coverage.

## 6.3 ApplyGuardrail and application-side checks

Use the ApplyGuardrail API when the application needs to evaluate content at a specific point in its pipeline, including before invoking the generation model. Normalize input before applying pattern/prompt-attack controls when the scenario calls for it.

Application-side validation remains important:
- Validate required fields and numeric ranges with API Gateway request models/JSON Schema.
- Validate model JSON against the expected schema.
- Compare factual claims with retrieved chunks when grounding matters.
- Redact PII in prompt, tool arguments/results, and application logs—not only in the final model response.
- Replay adversarial prompt cases as part of testing.

## 6.4 Guardrails across accounts

When one account centrally manages a guardrail and workload accounts must apply it:
- Configure the resource-based policy to allow intended workload accounts/principals.
- Ensure caller roles have the required `bedrock:ApplyGuardrail` permission.
- Scope permissions to approved guardrails and use least privilege.
- Test the actual cross-account request path and audit it.

A resource policy by itself does not automatically grant every caller all required identity permissions.

# 7. IAM, NETWORK SECURITY, DATA RESIDENCY, AND AUDIT

## 7.1 Least-privilege access

- Use IAM roles for AWS workloads instead of embedding long-lived access keys in application code or containers.
- Scope model invocation to approved model/model-profile ARNs where practical.
- For cross-account employees, use IAM Identity Center federation with the corporate identity provider and team-specific permission sets.
- Separate permission to invoke a model from permission to administer models, prompts, guardrails, or knowledge bases.
- Resource-based policies and caller identity policies may both be required for cross-account access.

## 7.2 Private Bedrock access from a VPC

```text
Private ECS / EC2 / Lambda-in-VPC
          |
          v
Interface VPC endpoint for bedrock-runtime
          |
          v
Amazon Bedrock Runtime
```

Use:
- The appropriate `bedrock-runtime` interface VPC endpoint
- Private DNS when appropriate
- Restrictive endpoint policy
- Restrictive IAM identity policy
- Correct security groups/DNS/network configuration
- Same-account/Region invocation logging configuration as required

A VPC endpoint allows supported private access to the service; it does not remove the need for IAM authorization.

## 7.3 Data residency and edge/on-premises patterns

For requirements that raw records must stay inside a plant/site:
- Perform ingestion, normalization, and PII redaction locally or on AWS Outposts where suitable.
- Send only approved/de-identified prompts to the regional Bedrock endpoint.
- Use the required private connectivity, such as Direct Connect and supported VPC endpoints.
- Define explicitly what data may leave the site, where it is logged, and how identifiers are handled.

**Important:** “Use a VPC endpoint” does not itself guarantee that data stays in a particular physical location. Residency is a complete data-flow and logging design.

## 7.4 Model invocation logging

Model invocation logs are useful for troubleshooting, auditing, and measuring application behavior. The supplied papers repeatedly use Bedrock invocation logging to CloudWatch Logs and/or S3.

- Configure logging in the appropriate account and Region.
- Include request metadata (for example, claim, experiment, workflow, cohort, or support-case identifiers) when supported and useful for correlation.
- Be careful: request/response logging may contain sensitive prompts, retrieved content, or PII.
- Redact/tokenize sensitive data before audit logging where required.
- Restrict access to log groups and S3 destinations; encrypt and set retention.
- Use CloudWatch Logs Insights to filter `ModelInvocationLog` records and project fields such as operation, model ID, principal, and token counts.
- Some logging/delivery capabilities have constraints by operation, account, Region, and destination. Confirm the operation is supported and the destination is configured correctly.

CloudTrail is for API activity/audit events (“who called what and when”). Bedrock invocation logging captures supported model request/response details. They complement each other; they are not interchangeable.

## 7.5 Request metadata and traceability

Attach safe business correlation identifiers to requests when supported, then correlate:
- Bedrock invocation logs
- CloudWatch metrics
- Tool runner metrics
- Workflow execution history
- User feedback/evaluation records

For client-side tool use, record the tool-use ID, tool name, latency, status, and outcome in the application. Bedrock does not automatically know the internal work performed by every client-side Lambda/tool; instrument the executor itself.

# 8. TOOLS, BEDROCK AGENTS, ACTION GROUPS, MCP, AND AGENTCORE

## 8.1 Tool use mental model

```text
User request
    |
    v
Foundation model decides tool is needed
    |
    v
Tool request (name + structured input)
    |
    v
Application/agent executes tool
    |
    v
Tool result returned to model
    |
    v
Model produces final response
```

The model proposes a tool call; the application or agent runtime executes it. Treat tool input as untrusted and validate it before making changes.

## 8.2 Bedrock Agents and action groups

An action group describes the operations an agent may invoke. An OpenAPI schema is used to describe operations, parameters, required fields, and allowed values.

Good schema practices:
- Use OpenAPI 3.0-compatible structure where required by the integration.
- Give every operation a unique `operationId`.
- Describe required and optional fields clearly.
- Validate inputs in the Lambda/API implementation even when the schema is present.
- Use confirmation for consequential actions such as settlement, dispatch, or other irreversible/high-impact operations. Where the supported action-group configuration provides confirmation controls (such as `x-requireConfirmation`), use them for the relevant operations.
- Keep the action contract narrow and least-privileged.

**Trap:** A model deciding to call `settleClaim` does not mean the application should execute it without policy validation or required human confirmation.

## 8.3 Client-side tool execution with Converse

Some applications use model tool requests but execute tools in their own code.

The client must:
1. Inspect the tool-use block.
2. Validate tool name and arguments.
3. Call the approved API/Lambda/retrieval service.
4. Capture result, errors, latency, and `toolUseId`.
5. Return the tool result in the expected Converse message structure.
6. Continue the conversation to get the final model response.

This pattern is useful when the app needs an application-owned search tool that calls `Retrieve` and then passes the returned chunks to the selected model.

## 8.4 MCP (Model Context Protocol)

MCP standardizes how AI applications discover and call tools/resources through a client-server model.

```text
FM application / Agent
        |
     MCP client
        |
        v
      MCP server
        |
        v
Vector search / internal API / tool
```

Use an MCP server when several applications or agent frameworks should access a shared tool contract rather than each implementing a different custom integration. MCP is a protocol boundary; it does not itself grant authorization or make a tool safe.

## 8.5 AgentCore Gateway

AgentCore Gateway can provide a standardized gateway for tools/targets such as Lambda. The source-paper pattern includes defining each tool schema, reading the input properties from the event, and invoking the appropriate prefixed tool.

Validate schema and permissions at the gateway and target. Do not assume a common gateway eliminates target-specific authorization, validation, logging, or error handling.

## 8.6 Strands Agents and multi-agent collaboration

Use specialized agents when tasks require distinct expertise and coordination—for example:
- Sensor/time-series analysis
- Maintenance-log interpretation
- Remediation planning

Give each agent a clear role, tools, and output contract. Use an orchestration layer (such as Agent Squad in the supplied scenarios) when agents must exchange intermediate findings, delegate subtasks, or coordinate dynamically.

A single agent with multiple tools can be simpler and cheaper when the task is straightforward. Multiple independent agents called sequentially and manually combined do not automatically provide collaboration or shared state.

# 9. EVALUATION: HOW TO PROVE A GENAI APP WORKS

## 9.1 Evaluation is more than “the answer looks good”

Evaluate at multiple levels:

```text
Input / prompt quality
       |
       v
Retrieval quality
       |
       v
Generation quality
       |
       v
Safety / policy compliance
       |
       v
Latency / cost / reliability
       |
       v
User usefulness and release decision
```

A model can be fluent but wrong. A RAG answer can be well-written but cite irrelevant chunks. A retrieval system can find relevant chunks while the model makes unsupported claims. Measure the layer that is failing.

## 9.2 RAG metrics

| Metric / evidence | Question it helps answer |
|---|---|
| Context relevance | Are the retrieved passages relevant to the question? |
| Context coverage | Does the retrieved context cover the needed evidence? |
| Faithfulness / groundedness | Is the answer supported by the retrieved context? |
| Correctness | Does the answer match the expected/reference answer? |
| Human usefulness/preference | Would the user or domain expert consider the answer useful? |
| Citation checks | Do the cited sources actually support the associated claims? |

Metric availability depends on the evaluation job type and supported dataset schema. Match the metric to the evaluation mode rather than assuming every metric is available in every job.

## 9.3 Retrieve-only vs retrieve-and-generate evaluation

- **Retrieve-only evaluation:** Best for isolating retrieval. Use prompt/query records and expected/reference information supported by the job format; metrics can include context relevance and context coverage.
- **Retrieve-and-generate evaluation:** Evaluates the generated answer as well as the RAG path. Include the supported prompt/output/retrieved-passage/reference-response fields.
- For a RAG system outside Bedrock, use the supported bring-your-own retrieval/inference data formats when available.
- If a job has dataset limits, split records into valid datasets/jobs rather than exceeding the limit.
- Keep the task type and dataset schema appropriate to each evaluation job.
- Reference contexts are not automatically required by every built-in RAG metric; follow the current job schema and only supply fields the metric/job needs.

## 9.4 Automatic evaluation, LLM-as-a-judge, and human review

| Method | Strength | Limitation |
|---|---|---|
| Automatic metrics / managed Bedrock evaluation | Repeatable, scalable, useful for regression | Metrics are proxies and can miss domain-specific failure |
| LLM-as-a-judge | Scales rubric-based quality assessment | Judge can be biased or wrong; calibrate against human labels |
| Human-based evaluation | Expert judgment for ambiguity, nuance, and high-risk cases | Slower and more expensive |
| Actual user feedback | Shows usefulness and preferences in production | Selection bias, noisy ratings, and feedback may not explain the failure |
| Synthetic canary | Tests critical journeys and release health | Not a replacement for broad semantic quality evaluation |

A strong strategy uses automated evaluation for broad coverage and sends flagged/ambiguous/high-risk cases to experts. Do not use a single evaluator model as the sole authority for high-impact decisions.

## 9.5 Dataset design

- Use representative, task-stratified datasets rather than only easy examples.
- Include realistic prompts, outputs, retrieved passages, and reference responses as required by the evaluation type.
- Store JSONL datasets in S3 in the documented schema.
- Respect per-job record limits and multi-turn conversation limits for the chosen evaluation feature.
- Keep a held-out set that is not used to tune the prompt.
- Version datasets, prompts, model identifiers, and evaluation configuration.
- Record model version/inference profile, prompt version, dataset version, metrics, and pass/fail outcome.

## 9.6 Automated release gates

```text
Candidate model/prompt
        |
        v
Run evaluation job(s)
        |
        v
Persist reports/results to S3
        |
        v
Compare scores with thresholds
        |
   +----+----+
   |         |
  PASS      FAIL
   |         |
Promote    Block release
```

Run separate evaluation jobs when the task type, model version, inference profile, or required evaluation dataset differs. Do not promote until every required job has completed and passed the defined thresholds. Use Step Functions/CI/CD orchestration to create an explicit pass/fail result.

## 9.7 Online feedback and cohort fairness

Collect production feedback with context such as:
- Prompt variant/version
- Model/inference profile
- Task category
- Cohort/group identifier, where appropriate and lawfully permitted
- User rating/comment and timestamp

Use offline evaluation to compare cohorts for quality disparity. A single overall score can hide a poor result for a specific user group. Apply privacy minimization and avoid collecting unnecessary sensitive data.

# 10. MODEL OPERATIONS, LATENCY, TOKEN BUDGET, AND COST

## 10.1 Key latency metrics

| Metric | What it tells you |
|---|---|
| Time to first token | How quickly a streaming user begins seeing output |
| Invocation latency | End-to-end invocation latency for a non-streaming request/path, as supported by the metric |
| Input/output token counts | Request size and generated output volume |
| Invocation count / errors / throttles | Traffic, reliability, and quota pressure |
| Log delivery health | Whether expected invocation logs are being delivered |

For a `ConverseStream` user experience, track time to first token. For a non-streaming invocation, use the appropriate invocation-latency measure. Avoid comparing unlike metrics as if they measure the same thing.

## 10.2 Token budget management

```text
Assemble system prompt + history + tools + retrieved chunks
                         |
                         v
             Estimate input token count
                         |
                         v
           Compare with model/context budget
                         |
              +----------+----------+
              |                     |
             Fits               Too large
              |                     |
              v                     v
           Invoke           Prune low-value context
                                    |
                                    v
                              Estimate again
```

- Use the token-estimation capability available for the selected model/request when appropriate.
- Keep the most relevant retrieved chunks; remove low-value context first.
- Summarize or trim older conversation history when allowed by the product behavior.
- Set an output-token limit appropriate to the task.
- Do not simply truncate the request arbitrarily if it can remove safety instructions, schema requirements, or critical evidence.

## 10.3 Prompt caching and token usage

Where supported, add cache checkpoints to reusable system instructions/tool definitions or other eligible prompt prefixes. Inspect returned cache-usage fields to verify that caching is actually happening.

Caching is beneficial only when the reusable prefix and request pattern meet the service/model requirements. Dynamic content placed before a reusable prefix can reduce cache hits.

## 10.4 Model routing and cascades

A model cascade can lower average cost by sending simple tasks to a smaller/cheaper model and escalating difficult or low-confidence requests to a stronger model.

```text
Incoming request
       |
       v
Classify task / estimate complexity
       |
       v
Small model
       |
       v
Quality / confidence / policy check
   |                    |
   v                    v
Pass                 Fail / complex
   |                    |
Return             Escalate to larger model
```

- Evaluate each task class separately.
- Define escalation conditions using measurable signals and tested policies.
- Avoid trusting an uncalibrated model-generated confidence score as the only gate.
- Compare quality, latency, and token cost before enabling a cascade.
- Record the route decision for observability.

AWS AppConfig can hold stage/tenant/task-specific configuration so routing thresholds and model IDs can be adjusted without hard-coding values in every Lambda. Use the AppConfig Agent Lambda extension where appropriate, read the local configuration endpoint, and apply controlled rollout/validation.

## 10.5 On-demand vs Provisioned Throughput

- **On-demand:** Good starting point for variable or uncertain demand; no capacity commitment.
- **Provisioned Throughput:** Consider for predictable high usage or throughput requirements. Size using observed invocation and token usage, create the appropriate capacity for the model, wait until it is `InService`, and invoke the provisioned model ARN.
- For custom models, verify the supported provisioning mode and commitment terms.
- Do not provision based only on peak request count: tokens per request and concurrency matter.

## 10.6 SageMaker large-model inference

For large open-weight models on SageMaker AI:
- Use a suitable Large Model Inference (LMI) container.
- Select GPU instances and memory based on model size/context/batch.
- Configure tensor parallelism when model weights must be distributed across devices.
- Consider continuous/rolling batching where supported.
- Allow realistic model-load/startup timeouts.
- Benchmark with representative input/output lengths and concurrency.
- Scale endpoint variants using a useful utilization signal. If the relevant workload is token-generation bound, a custom metric such as tokens processed per instance may be more informative than CPU alone.
- Use Application Auto Scaling target tracking where supported.

## 10.7 Lambda integration limits and patterns

- Lambda is useful for request validation, preprocessing, model invocation, routing, and lightweight tool execution.
- Increase timeout to cover expected model latency, but remain within the current Lambda maximum (the sample notes use 900 seconds).
- Do not use a synchronous Lambda/API request for work that should be asynchronous or can exceed client timeouts.
- For long-running reports, submit an async job and store results in S3 or another durable destination.
- Watch concurrency, throttling, errors, and token-related metrics.
- Use idempotency for retryable worker tasks that cause side effects.

# 15. DEVELOPER PRODUCTIVITY AND TESTING PRACTICES

## 15.1 AI-assisted coding

Use IDE chat with relevant open-file/workspace context for code suggestions, test scaffolding, and refactoring. Review generated diffs; run unit/integration tests, linters, dependency/security scans, and code review before merging.

AI-generated code is a draft. Never treat a suggested IAM policy, tool executor, or validation path as secure merely because the code compiles.

## 15.2 Troubleshooting in the correct order

For a RAG quality regression:
1. Freeze a fixed query set.
2. Call `Retrieve` to inspect chunks, metadata, locations, and scores.
3. Check source freshness and ingestion status.
4. Check metadata filters and access boundaries.
5. Check chunking and embedding/index configuration.
6. Only then experiment with reranking, query rewriting, prompt changes, or model changes.
7. Evaluate the complete retrieve-and-generate path after the retrieval issue is understood.

For a latency regression:
1. Separate time to first token from total invocation latency.
2. Compare model, Region, input/output tokens, cache usage, and concurrency.
3. Inspect throttles, errors, endpoint/throughput capacity, and tool latency.
4. Determine whether delay is in retrieval, model inference, orchestration, or response transport.
5. Change one variable at a time and rerun a representative test.

For a safety regression:
1. Identify whether unsafe content originates in user input, retrieved content, tool output, or generated output.
2. Apply input and output controls at the appropriate stages.
3. Redact sensitive data before logging.
4. Replay adversarial cases.
5. Measure both blocking effectiveness and false positives.

# 17. EXAM DECISION RULES AND COMMON TRAPS

1. **Diagnose before optimizing.** For RAG ranking problems, inspect `Retrieve` results before adding reranking or rewriting the prompt.
2. **Match the metric to the layer.** Retrieval metrics do not prove the generated answer is faithful; generation metrics do not prove the right documents were retrieved.
3. **Version every important release artifact.** Prompt, model, dataset, index/embedding configuration, evaluation results, and approval should be traceable.
4. **Do not skip source freshness.** An answer can be semantically plausible but wrong because ingestion has not completed or an old index remains.
5. **Metadata is a boundary.** Include document version, tenant, locale, jurisdiction, and entitlement when they affect the answer.
6. **Guardrails are not IAM.** Content filters do not authorize a user to read a record or call a tool.
7. **IAM is not PII redaction.** Permissions do not remove sensitive values from prompts, tool results, or logs.
8. **Logging can create a privacy risk.** Invocation logs may contain prompts and output; redact, restrict, encrypt, and retain deliberately.
9. **A tool schema is not sufficient validation.** Validate arguments in the executor and require confirmation for high-impact actions.
10. **Prompt caching is not answer caching.** The first reuses eligible input-prefix processing; the second reuses generated results.
11. **Use asynchronous patterns for asynchronous work.** Long reports should not depend on a browser waiting on a synchronous API indefinitely.
12. **Evaluation must be automated to gate CI/CD.** A stored report requiring manual inspection is not the same as a pipeline pass/fail signal.
13. **Human review belongs where ambiguity/risk is high.** Do not treat an LLM judge as infallible.
14. **Use the right service for each modality.** Transcribe for speech-to-text, Data Automation for supported multimodal extraction, Processing for repeatable normalization.
15. **Check API compatibility per model.** Do not assume `ConverseStream`, `InvokeModel`, or a particular payload works for every model.
16. **Scale on a workload-relevant signal.** Token generation may need token-based/custom metrics; CPU alone may not reflect the bottleneck.
17. **Cross-account access often needs both sides.** Resource policy and caller IAM permission must both allow the operation.
18. **A vector index has a contract.** Model dimensions, vector/text/metadata fields, engine, index, and permissions must agree.
19. **Changing embeddings is a data migration.** Plan full, consistent re-embedding/re-indexing and systematic evaluation.
20. **Keep evidence for every claim.** Citations must point to actual retrieved references, and critical claims should be checked against the cited passage.
