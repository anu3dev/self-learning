# Kiro + AI-DLC — Complete Revision Notes

## 1. Kiro: Vibe vs Spec

Kiro supports two different development approaches:

### Vibe

**Free-form conversation**

* Developer describes what they want.
* AI responds and helps build it.
* Flexible and conversational.

### Spec

**Structured and plan-first**

* Requirements are clarified first.
* AI creates a structured plan/specification.
* Developer reviews and approves before implementation.

### Easy Memory

> **Vibe = Conversation**
> **Spec = Structure + Plan**

---

# 2. Subagents

A **subagent** is a separate AI agent that handles a delegated task.

### Important characteristics

* Each subagent gets its **own context window**.
* Its work does not clutter the main conversation.
* Up to **4 subagents can run simultaneously**.
* Progress can be viewed using **Ctrl+G**.
* Two built-in subagents:

  * **Context Gatherer** — explores the codebase.
  * **General-purpose agent** — handles other tasks.
* Custom subagents can be created with their own:

  * Tools
  * Permissions
  * Limited access

### Parallelism

* Independent tasks → can run simultaneously.
* Dependent tasks → wait for prerequisite tasks.
* Results are summarized and returned to the main agent.

### Memory Trick

> **Subagent = Separate context + separate task + controlled permissions**

---

# 3. Agent Hooks

Traditional AI coding is **reactive**:

> Developer asks → AI responds.

**Agent Hooks make the IDE proactive.**

They are **event-driven AI automations** that automatically trigger actions when specific events occur in the workspace.

### Reactive vs Proactive

| Without Hooks              | With Hooks               |
| -------------------------- | ------------------------ |
| Developer initiates action | Event initiates action   |
| Reactive                   | Proactive                |
| Ask → response             | Event → automatic action |

---

# 4. Common Agent Hook Patterns

### 1. Lint & Format on Save

**Trigger:** File Saved Event
**Action:** Shell command

Examples:

* ESLint
* Prettier
* Black

Benefit:

* Files are formatted automatically.
* Shell command → no agent loop.
* No AI credit cost.

---

### 2. Test Sync

**Trigger:** File Saved Event
**Action:** Agent Prompt

When implementation changes, Kiro updates corresponding tests.

> **Code changes → Tests stay in sync**

---

### 3. Security Scanning

**Trigger:** Agent Stop Event

After the agent finishes:

* Review changed files.
* Look for hardcoded secrets.
* Fix them.

---

### 4. Documentation Sync

**Trigger:**

* File Saved Event
* Or `postToolUse`

When code changes, update:

* README
* Inline comments
* API documentation

---

### 5. Tool Gating

**Trigger:** `preToolUse`

Used as a **safety gate**.

Example:

> Agent attempts `rm -rf` → hook can intervene/block it.

Useful for:

* Shared workspaces
* Preventing destructive commands
* Controlling dangerous operations

---

### 6. Audit Logging

**Trigger:** `postToolUse`

Logs what the agent did.

Useful for:

* Compliance
* Debugging
* Auditing
* Understanding long agent sessions

---

### 7. i18n Sync

**Trigger:** File Saved Event on locale files.

When English strings change:

* Other language files can be marked:

  * `NEEDS_TRANSLATION`
  * `NEEDS_REVIEW`

---

### 8. MCP Integration

Example:

**File Saved Event → Agent Prompt → Figma MCP**

When CSS/HTML changes, Kiro can validate the implementation against the Figma design.

---

## Hook Trigger Cheat Sheet

| Trigger              | Best Use                                  |
| -------------------- | ----------------------------------------- |
| **File Saved Event** | Format, tests, docs, i18n                 |
| **preToolUse**       | Safety / tool gating                      |
| **postToolUse**      | Logging / actions after tool execution    |
| **Agent Stop Event** | Comprehensive review after agent finishes |

### Memory

> **preToolUse = Before**
> **postToolUse = After**
> **Agent Stop = Review after agent finishes**

# 5. Steering

AI models are fundamentally **stateless** between sessions.

Therefore, Kiro needs persistent context to consistently understand:

* Project requirements
* Technology choices
* Architecture
* Team conventions
* Domain rules

**Steering supplies this missing context.**

### Context Layers

1. **Standard context**

   * Prompt
   * Code
   * Chat history

2. **Foundational files**

   * Product
   * Technology
   * Structure

3. **Custom guidance**

   * Organization-specific rules
   * Domain-specific rules
   * Team conventions

4. **Result**

   * More relevant and consistent AI responses

---

# 6. Foundational vs Custom Steering

## Foundational Steering

Generated from the repository.

Kiro analyzes the project and creates a starting set of:

* `product.md`
* `tech.md`
* `structure.md`

Useful for quickly establishing basic project context.

---

## Custom Steering

**Human-authored Markdown** containing knowledge specific to your organization/team.

Can come from:

* Internal wikis
* MCP sources
* Existing documentation

### Examples

* `api-rest-conventions.md`
* `logging-standards.md`
* `testing-unit-patterns.md`
* `components-form-validation.md`
* `security-practices.md`

---

# 7. Steering Locations

There are two main locations.

### Workspace Steering

```text
.kiro/steering
```

* Local to the project.
* Applies to that specific project.
* Included by default.

### Global Steering

```text
~/.kiro/steering
```

* Shared across projects.
* Good for reusable patterns and organization-wide guidance.

### Memory

> **Workspace = One project**
> **Global = Every project**


# 9. MCP — Model Context Protocol

**MCP = Model Context Protocol**

It provides a standardized way for AI agents to access **tools and context from external systems**.

It is:

* Not proprietary to Kiro.
* A middle layer between AI agents and external capabilities.
* Usable with local or remote servers.

### Mental Model

```text
AI Agent
   ↓
  MCP
   ↓
External Tool / Data / System
```

---

# 10. Three MCP Primitives

The three fundamental MCP primitives are:

### 1. Tools

Callable functions that allow the agent to perform actions.

Think:

> **Tools = Agent's hands**

---

### 2. Prompts

Reusable prompt structures/guidance exposed by an MCP server.

---

### 3. Resource Templates

Templates for accessing contextual resources/data.

### Memory

> **MCP = Tools + Prompts + Resource Templates**

---

# 11. MCP Tools

A tool is essentially a **callable function** with a defined schema.

Important characteristics:

* Callable function
* Agent's "hands"
* Defined schema
* Multiple tools can exist on one server

Example:

**AWS Documentation MCP**

The agent can call a documentation-search tool rather than relying only on its internal knowledge.

---

# 12. Four Ways to Use MCP Tools

### 1. Direct Question

Simply ask:

> "Tell me about Amazon Bedrock."

Kiro chooses the appropriate tool.

### 2. Specific Tool Request

Specify the source:

> "Search AWS documentation for ECS task definitions."

### 3. Explicit Context

Explicitly identify server and tool:

```text
#[aws-docs] search_documentation
```

### 4. Local + External Context

Combine your code with external knowledge:

> "Based on my code, optimize it using AWS best practices."

# 16. MCP Context Considerations

Important principles:

### Servers Cost Context

Connecting many servers can consume context.

### Definitions Load In

Tool definitions themselves consume context.

### Tools ≠ Guidance

MCP tools provide capabilities, but **steering provides guidance**.

### Powers Load on Demand

Capabilities can be activated when relevant rather than keeping everything active all the time.

# 17. Kiro Powers

**Kiro Powers** are specialized capabilities that give the AI agent expertise for specific tools/frameworks.

Each Power combines:

1. **MCP server connections**
2. **Steering files containing best practices**

### Example

**Figma Power**

* Figma MCP connection
* Figma/design-to-code guidance

**Supabase Power**

* Supabase MCP
* Supabase-specific guidance

### Key Characteristic

Powers are **composable** and activate intelligently based on the task.

Example:

> Ask Kiro to convert a Figma design into code → Figma Power guidance automatically activates.

# 18. AI-DLC — Why It Exists

There are two problematic extremes.

## AI-Assisted Development

AI helps with small tasks:

* Autocomplete
* Unit tests
* Explaining code
* Small isolated changes

### Problem

Safe, but the developer still performs most of the thinking and coordination.

---

## AI-Autonomous / Vibe Coding

You give the AI a large request and it builds the application end-to-end.

### Problem

It can be:

* Fragile
* Difficult to trace
* Difficult to maintain
* Risky at scale

---

## The Gap

> **AI-assisted = safer but slower**

> **Vibe coding = faster but potentially risky**

AI-DLC aims to combine:

**Speed + Control + Quality**

---

# 19. Missing Context Problems

When the AI doesn't have enough context, three common problems appear:

### 1. Wrong Assumptions

AI fills missing information with assumptions.

### 2. Hallucinated Requirements

AI invents requirements that were never specified.

### 3. Inconsistent Design

Different parts of the solution may follow inconsistent design decisions.

---

# 20. AI-DLC Context Loop

AI-DLC solves this using a continuous loop:

### 1. Human Proposes Intent

Human states:

* What they want
* Why they want it

### 2. AI Asks Structured Questions

AI identifies gaps instead of silently guessing.

### 3. Answers Become Durable Context

Human answers are written down and carried forward.

### Result

> **Context accumulates → AI becomes more effective → quality compounds**

# 25. The Approval Gate ⭐

One of the most important AI-DLC concepts.

**Every stage ends with an approval gate.**

Process:

```text
AI proposes
     ↓
Human reviews
     ↓
Approve OR Request Changes
     ↓
Next stage
```

Nothing moves forward without **explicit human sign-off**.

### Why?

This maintains:

> **Human-in-the-loop control**

# 26. Steering Rules vs Generated Documents ⭐

These two are both Markdown but serve completely different purposes.

|            | Steering Rules       | Generated Docs         |
| ---------- | -------------------- | ---------------------- |
| Role       | **Input**            | **Output**             |
| Created by | Human/org            | AI workflow            |
| Location   | `.kiro/steering`     | `aidlc-docs`           |
| Purpose    | Guide agent behavior | Capture decisions      |
| Nature     | Prescriptive         | Durable project record |

### Steering

> **"How should the AI behave?"**

### Generated Docs

> **"What did we decide?"**

### Critical Memory

**Steering = Rules**

**aidlc-docs = Decisions / Source of Truth**

---

# 27. Just-in-Time Steering Loading

Kiro does not need to load every rule at once.

### Step 1 — Always On

`core-workflow.md`

Acts as a dispatcher and routes to the appropriate rules.

### Step 2 — Start

Common rules load.

### Step 3 — Current Stage

Only the current stage's detailed rules load.

Example:

* Requirements stage → requirements rules
* Construction → code-generation rules

### Step 4 — Extensions

Optional rules are loaded only when explicitly opted into.

### Why?

> **Keep context lean and relevant.**

# 28. Greenfield vs Brownfield

### Greenfield

A **new project**.

No existing application/codebase to reverse engineer.

### Brownfield

An **existing project**.

AI-DLC additionally performs reverse engineering to understand the existing system.

For example:

* Existing code
* APIs
* Existing architecture

### Memory

**Greenfield = New**

**Brownfield = Existing + Reverse Engineering**

# 29. Question → Document → Approval Loop ⭐

AI-DLC does not rely only on chat for important decisions.

The workflow is:

### Step 1 — AI Writes Questions

Questions are written into a Markdown file.

### Step 2 — Human Answers

Fill in the answer tags.

Typically:

* A
* B
* C
* X

### Step 3 — Signal Ready

Return to chat and tell Kiro the answers are ready.

### Step 4 — AI Validates

Kiro:

* Reads the file
* Validates answers
* Identifies ambiguity
* Generates the next artifact

# 30. Why Files Instead of Chat?

Three important reasons:

### 1. Durable Record

Decisions persist on disk.

### 2. Team Contribution

Other team members can contribute.

### 3. Survives Context Resets

Information isn't lost when chat context changes.

### Best Practice

Add a short justification next to each answer.

Example:

```text
Answer: B
Reason: The application is internal and used only by employees.
```

This gives the AI richer context.

# 32. Five Habits for Clean AI-DLC Context

### 1. Reset at Every Gate

Treat each approval gate as a clean checkpoint.

### 2. Decline "Compact Context"

Avoid unnecessarily compressing away important context.

### 3. Resume via `aidlc-state.md`

Use the durable state file to continue the workflow.

### 4. Guard Exploration Mode

Prevent uncontrolled exploration from polluting the workflow/context.

### 5. Layer Organization Rules

Add your organization's own rules on top of the AI-DLC workflow.

# 33. AI-DLC Mental Model

Think of context like **computer RAM**.

### Chat = Volatile RAM

Temporary context.

### Files = Disk

Persistent context.

Therefore:

> **Flush context → Save to files → Reload what is needed**

This is one of the central ideas behind maintaining clean context during long AI-DLC workflows.

# 37. AI-DLC Artifacts

AI-DLC introduces several important artifacts.

## Intent

A high-level statement of:

* Purpose
* Business goal
* Feature
* Technical outcome

It is the starting point for AI-driven decomposition.

---

## Unit

A **cohesive, self-contained work element** derived from an Intent.

Think:

> **Intent → Units**

A Unit is similar conceptually to a:

* Subdomain in DDD
* Epic in Scrum

---

## Bolt

The **smallest iteration** in AI-DLC.

Used for rapid implementation of a Unit or set of tasks.

Similar conceptually to a **Sprint**, but intended for shorter, high-velocity delivery cycles.

### Hierarchy

```text
Intent
  ↓
Unit
  ↓
Bolt
```

# 40. AI-DLC Detailed Lifecycle

The more detailed methodology includes:

### Initialization

One-time bootstrap.

It:

* Prepares AI-DLC workspace
* Detects project context
* Determines greenfield/brownfield
* Detects languages/frameworks/build tools
* Creates intent/state
* Determines lifecycle scope

### Ideation

Turns a raw idea into an approved Intent.

Includes:

* Problem
* Outcome
* Primary users
* Scope
* Feasibility
* Optional market research
* Team formation
* Rough mockups

Ends with approval into Inception.

### Inception

Turns:

**Intent → Units**

Uses collaborative **Mob Elaboration** involving:

* Product Owner
* Developers
* AI

Outputs include:

* Unit Definition
* NFR definition
* Risks and mitigations
* Measurement criteria
* Suggested Bolts

### Construction

Turns:

**Units → Deployment Units**

Includes:

* Domain Design
* NFRs
* Cloud patterns
* Logical design
* Code generation
* Testing

Developers validate AI-generated outputs.

### Operations

Focuses on:

* Deployment
* Observability
* Maintenance
* Telemetry analysis
* Anomaly detection
* SLA violation prediction
* Incident recommendations
* Resource scaling
* Performance tuning
* Fault isolation

AI can propose actions, while developers validate them against SLA and compliance requirements.

# 42. Key Principles of AI-DLC

Five important principles:

### 1. Reimagine Rather Than Retrofit

AI-DLC is designed from first principles for AI integration.

### 2. Reverse the Conversation Direction

Instead of always:

> Human asks → AI answers

AI can drive the workflow by:

> AI asks → Human approves

### 3. Integration of Design Techniques

Design methodologies such as **DDD** are integrated into the process.

### 4. Align With AI Capability

Balance AI capabilities with required human oversight.

### 5. Streamline Responsibilities

AI-DLC helps developers move beyond traditional specialization silos.
