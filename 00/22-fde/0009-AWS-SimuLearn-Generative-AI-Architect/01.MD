# AWS AgentCore — End-to-End Developer Architecture & Revision Notes

> **Purpose:** This note explains the complete architecture of an AWS AgentCore-based AI application from a developer's perspective — from the browser/UI all the way to AgentCore, RAG, Gateway, Lambda, Secrets Manager, RDS, and back to the user.
>
> The goal is to understand **what each AWS service does, why it is needed, how the services communicate, and how a real production application is wired together.**

---

# 1. Temperature — Quick AI Concept

Temperature controls the randomness of an AI model's response.

- **Lower temperature (closer to `0`)**
  - More focused
  - More deterministic
  - Better for factual/technical tasks

- **Higher temperature (closer to `1`)**
  - More varied
  - More creative
  - Useful for creative tasks

> **Memory:** Low temperature → predictable. High temperature → creative.

# 2. Core AgentCore + Gateway + Lambda + Database Flow

The most important flow from this topic is:

```text
Agent
  ↓
AgentCore Gateway
  ↓
Gateway Target
  ↓
Lambda
  ↓
Secrets Manager
  ↓
RDS
  ↓
Lambda
  ↓
Gateway
  ↓
Agent
What happens?
The Agent determines that it needs some external/live information.
The Agent calls a tool exposed through AgentCore Gateway.
Gateway identifies the configured Target.
The Target invokes the Lambda.
Lambda retrieves the database credentials/secret from Secrets Manager.
Lambda connects to RDS.
Lambda executes the required database operation.
Lambda returns the business result.
Gateway returns the tool result to the Agent.
Agent uses the result to generate the final response.
Critical security point

The Agent does NOT receive the database password.

The secret stays inside the backend flow:

Lambda → Secrets Manager → DB

The Agent receives only the required business result:

{
  "order_id": "12345",
  "status": "SHIPPED"
}

NOT:

{
  "username": "dbuser",
  "password": "mypassword123",
  "host": "database..."
}
3. Why Do We Need AgentCore Gateway?

The AgentCore Agent uses Gateway when it needs to access external tools/backend capabilities that have been exposed through that Gateway.

Think of Gateway as a tool access layer / tool router.

For example:

AgentCore Gateway
│
├── get_order_details
│       ↓
│     Lambda
│
├── check_inventory
│       ↓
│     Lambda
│
├── cancel_order
│       ↓
│     Lambda
│
└── search_products
        ↓
      Lambda

The Agent doesn't need to know how every backend system works.

It simply knows:

"I have a tool called check_inventory."

Gateway knows:

check_inventory
      ↓
Target
      ↓
Lambda
4. What Does "Adding a Target" Mean?

Adding a target means:

Registering/configuring a backend capability that the AgentCore Gateway can invoke.

For example:

AgentCore Gateway
       │
       └── Target
             │
             └── cs_bot_lambda_diy

The target establishes the relationship:

Tool
  ↓
Target
  ↓
Backend implementation
  ↓
Lambda
Important distinction
Target ≠ another Lambda

Instead:

Target = configured connection/entry that tells Gateway where/how to invoke the backend tool.

10. Step 5 — Lambda Needs Database Credentials

Lambda should NOT contain hard-coded credentials.

❌ Bad
username = "admin"
password = "mypassword123"
✅ Better

Lambda has an environment variable pointing to the secret:

DB_SECRET_ARN =
arn:aws:secretsmanager:us-east-1:123456:secret:rds-secret

The Lambda therefore knows:

"I know which Secrets Manager secret contains my DB credentials."

11. Step 6 — Lambda → Secrets Manager

Lambda calls Secrets Manager.

Lambda
   │
   │ GetSecretValue
   ↓
Secrets Manager

Secrets Manager returns the credentials to Lambda:

  "username": "dbuser",
  "password": "********",
  "host": "mydb.xxxxx.rds.amazonaws.com",
  "port": 3306
}
🚨 Critical
Agent NEVER gets this secret.

The credentials remain inside the backend execution flow.

18. Node/Java → AgentCore Runtime

Node/Java can directly invoke a deployed AgentCore Runtime.

You do NOT need AgentCore Gateway just to invoke the Agent.

The relationship is:

     │
     │ InvokeAgentRuntime
     ▼
AgentCore Runtime
     │
     ▼
Agent

Gateway is used later if the Agent needs to call tools.

Therefore:

Node/Java → AgentCore Runtime

and:

Agent → Gateway → Tools

are two different relationships.

20. AgentCore Runtime Invocation

The API operation is:

InvokeAgentRuntime

Conceptually, the HTTP API looks like:

POST /runtimes/{agentRuntimeArn}/invocations?qualifier=DEFAULT

The SDK handles the low-level request construction for you.

21. Node.js Example

Install the AWS SDK:

npm install @aws-sdk/client-bedrock-agentcore

Example:

import {
  BedrockAgentCoreClient,
  InvokeAgentRuntimeCommand
} from "@aws-sdk/client-bedrock-agentcore";

import crypto from "crypto";

const client = new BedrockAgentCoreClient({
  region: process.env.AWS_REGION
});

const agentRuntimeArn =
  process.env.AGENTCORE_RUNTIME_ARN;

export async function askAgent(userMessage) {

  const sessionId = crypto.randomUUID();

  const payload = JSON.stringify({
    prompt: userMessage
  });

  const command = new InvokeAgentRuntimeCommand({
    agentRuntimeArn,
    runtimeSessionId: sessionId,
    payload: Buffer.from(payload),
    qualifier: "DEFAULT"
  });

  const response = await client.send(command);

  const chunks = [];

  for await (const chunk of response.response) {
    chunks.push(
      Buffer.from(chunk).toString("utf-8")
    );
  }

  return chunks.join("");
}

              ↓

The most important sentence to remember is:

Node/Java directly invokes the deployed AgentCore Runtime using its Runtime ARN and InvokeAgentRuntime. The Agent then decides whether it needs the Knowledge Base or a Gateway-exposed tool. Gateway routes tool requests to configured targets, such as Lambda. Lambda securely retrieves credentials from Secrets Manager, accesses RDS, and returns only the required business result to the Agent.
