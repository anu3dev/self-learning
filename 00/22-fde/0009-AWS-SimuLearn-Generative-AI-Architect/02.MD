# 01. Bedrock vs AgentCore — The Easiest Mental Model

Remember this:

```
BEDROCK
=
AI BRAIN + AI CAPABILITIES

AGENTCORE
=
AGENT PRODUCTION INFRASTRUCTURE
```

More specifically:

```
BEDROCK
├── Foundation Models
├── Model Inference
├── Knowledge Bases
├── Bedrock Agents
├── Guardrails
└── Other AI capabilities


AGENTCORE
├── Runtime
├── Gateway
├── Memory
├── Identity
├── Policies
└── Agent production infrastructure
```

---

# 02. When To Use What?

## Scenario 1 — Simple AI Chat

Requirement:

> "User enters text and AI responds."

Use:

```
React
 ↓
Node
 ↓
Bedrock Runtime
 ↓
Foundation Model
```

AgentCore is probably unnecessary.

---

## Scenario 2 — Chat With Company Documents

Requirement:

> "Answer questions using our company documents."

Use:

```
React
 ↓
Node
 ↓
Bedrock
 ↓
Knowledge Base
 ↓
S3 / Vector Store
```

Again, AgentCore may not be required.

---

## Scenario 3 — AI Agent With Tools

Requirement:

> "Find my order, check inventory and cancel my order."

Now the AI needs tools.

Possible architecture:

```
Application
     ↓
Bedrock Agent
     ↓
Tools / Actions
     ↓
Lambda / APIs
     ↓
Business Systems
```

You can build this using Bedrock's managed Agent capabilities.

---

## Scenario 4 — Custom Agent Application

Suppose you want to write your own agent using:

```
Python
+
Strands SDK
+
Bedrock
```

And deploy it as your own production agent.

Then:

```
Your Agent Code
       ↓
AgentCore Runtime
       ↓
Production Agent
```

This is a strong AgentCore use case.

---

## Scenario 5 — Custom Agent + Multiple Tools

Now suppose your agent needs:

```
getOrder()
cancelOrder()
getInventory()
createReturn()
searchProducts()
```

Instead of embedding every backend integration directly inside the agent:

```
Agent
 ├── Lambda
 ├── REST API
 ├── Database
 ├── MCP Server
 └── Another Agent
```

you can use:

```
Agent
   ↓
AgentCore Gateway
   ↓
 ├── getOrder
 ├── cancelOrder
 ├── getInventory
 ├── createReturn
 └── searchProducts
```

This creates a centralized tool-access layer.

---

## Scenario 6 — Enterprise Production Agent

If you need:

-  Custom agent runtime 
-  Authentication 
-  Tool governance 
-  Centralized access 
-  Policies 
-  Guardrails 
-  Memory 
-  Observability 
-  Multiple agents 
-  Multiple tools 

AgentCore becomes much more relevant.

Typical architecture:

```
                USER
                  │
                  ▼
              Application
                  │
                  ▼
            AgentCore Gateway
                  │
                  ▼
           AgentCore Runtime
                  │
                  ▼
                Agent
              /       \
             /         \
            ▼           ▼
      Knowledge Base   Tools
                         │
                         ▼
                      Gateway
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
           Lambda       API       MCP
```

The exact topology can vary; Gateway can also be used to front Runtime so it becomes the governed entry point for the agent. AWS documents this pattern for centralized authorization, Guardrails, interceptors and observability.

# 03. Guardrails — Where Do They Belong?

This is where your original question needs an important correction.

Guardrails are an Amazon Bedrock capability.

They can be used with:

```
Bedrock Model Inference
Bedrock Agents
Bedrock Knowledge Bases
Bedrock Flows
```

For example:

```
User
 ↓
Bedrock Agent
 ↓
Guardrail
 ↓
Model
```

or:

```
User
 ↓
Knowledge Base
 ↓
Guardrail
 ↓
Generated Answer
```

AWS explicitly supports Guardrails for model inference, Agents and Knowledge Bases. 

---

# 04. Guardrails + AgentCore

AgentCore can also use Bedrock Guardrails at the Gateway policy layer.

For example:

```
User
 ↓
AgentCore Gateway
 ↓
Guardrail / Policy
 ↓
AgentCore Runtime
 ↓
Agent
```

This is a different placement.

Here the Guardrail is being used as part of the Gateway's governance/policy layer.

AWS documents Guardrails in AgentCore policies for content filters, prompt attacks and sensitive information detection. 

Therefore:

> Guardrails are a Bedrock capability that AgentCore can also leverage.

Do NOT memorize:

```
Guardrail = AgentCore feature
```

Memorize:

```
Guardrail
    ↓
Amazon Bedrock capability

AgentCore
    ↓
Can use it through its governance/policy layer
```

---

# 05. Knowledge Base + AgentCore

Same idea.

Knowledge Base is a Bedrock capability.

You can use it with a Bedrock Agent:

```
Bedrock Agent
      ↓
Knowledge Base
```

You can also use a managed Bedrock Knowledge Base through AgentCore Gateway.

AWS supports exposing a managed Knowledge Base as a Gateway target, allowing an MCP-compatible agent/client to query it as a tool. 

So:

```
AgentCore Agent
      ↓
AgentCore Gateway
      ↓
Knowledge Base Target
      ↓
Bedrock Knowledge Base
```

This is another example of:

> AgentCore does not replace Bedrock.

It can connect/govern Bedrock capabilities.

---

# 06. Very Important: "Can I Attach Everything to Everything?"

NO.

Don't think of AWS AI services as Lego blocks where every component can be attached directly to every other component.

Instead, ask:

> "Who owns this capability and through what interface does it connect?"

Example:

```
Knowledge Base
    ↓
Owned by Bedrock

Gateway
    ↓
Owned by AgentCore

Runtime
    ↓
Owned by AgentCore

Guardrails
    ↓
Owned by Bedrock

Lambda
    ↓
AWS Lambda
```

Then determine how they integrate.

For example:

```
AgentCore Gateway
       ↓
Knowledge Base Target
       ↓
Bedrock Knowledge Base
```

or:

```
Bedrock Agent
       ↓
Knowledge Base
```

# 07. Bedrock Agent vs AgentCore Runtime

This is probably the most important comparison for you.

## Bedrock Agent

AWS manages the Agent experience.

Conceptually:

```
You configure:

Instructions
+
Model
+
Knowledge Base
+
Actions

        ↓

AWS Bedrock Agent
```

You don't write the entire orchestration runtime yourself.

---

## AgentCore Runtime

You write your agent application.

For example:

```
Your Python Code

agent.py
tools.py
prompts.py
logic.py

        ↓

AgentCore Runtime
```

You have much more control over the application/runtime architecture.

So:

```
Bedrock Agent
=
Managed Agent capability

AgentCore Runtime
=
Run YOUR agent application
```

# 16. The Most Important Architecture Rule

Don't start by asking:

> "Should I use Bedrock or AgentCore?"

Instead ask:

```
1. Do I need an LLM?
       ↓
   Bedrock

2. Do I need enterprise knowledge?
       ↓
   Knowledge Base

3. Do I need AI safety?
       ↓
   Guardrails

4. Do I need an Agent?
       ↓
   Bedrock Agent
   OR
   Custom Agent

5. Is it my custom agent that needs
   production runtime?
       ↓
   AgentCore Runtime

6. Does the Agent need tools/APIs?
       ↓
   AgentCore Gateway

7. Does the tool need business data?
       ↓
   Lambda / API
       ↓
   RDS

8. Does the tool need credentials?
       ↓
   Secrets Manager
```
